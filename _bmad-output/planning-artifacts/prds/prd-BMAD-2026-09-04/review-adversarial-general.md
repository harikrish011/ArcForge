# Adversarial Review — Parking Spot Finder PRD

Reviewer role: skeptical stakeholder pressure-testing before greenlighting, given the PRD's stakes were deliberately set to "Launch-grade."

## Overall take

This PRD is unusually well-disciplined about *tagging* its own uncertainty (`[ASSUMPTION]`, `[NOTE FOR PM]`, an indexed §9), but that discipline is inconsistently applied to the places that actually matter most: the radius-expansion mechanic directly contradicts the PRD's own "fixed, non-adjustable radius" non-goal in three separate locations, the core Free/Paid trust claim has zero mechanism to catch or disclose a wrong or stale classification even though the entire Vision section is built on users trusting that badge "without double-checking," and a "launch-grade" success-metrics section defines session-level percentages with no instrumentation mechanism that could produce them under the PRD's own no-persistence privacy stance. None of these are exotic edge cases — they sit on the two or three sentences a downstream architect or story-writer would read first.

## Findings

1. **[CRITICAL] Radius-expansion FR directly contradicts the "fixed, non-adjustable radius" non-goal — stated three separate times**
   - Location: §5 Non-Goals — "No user-adjustable search radius in v1 — fixed at 1km." §3 Glossary, Radius — "Fixed at 1km for MVP; not user-adjustable (see FR-3, Non-Goals)." §4.2 FR-3 "Out of Scope: User-adjustable radius (Non-Goal, v1)." Versus §4.2 FR-6 — "the zero-result state names the searched radius and offers `[ASSUMPTION: a one-tap expansion, e.g. to 2km]`" — and UJ-2's whole climax runs on this: "the first search returns zero results within 1km ... he expands it → sees a Paid spot."
   - Why it matters: an "expand to 2km" action *is* the user adjusting the radius, full stop — it's the entire content of UJ-2, one of only two key journeys, and it's exercised in the MVP-must-have scope (§6.1 lists FR-1–FR-8 as Must Have, including FR-6). A downstream architect implementing FR-3's endpoint literally cannot tell whether the API contract allows a caller-supplied `radius` value at all, because three passages say no and one Must-Have FR requires yes.
   - Fix: either (a) reword the non-goal/glossary to "no *arbitrary* user-adjustable radius — only a single fixed one-tap expansion path exists (1km → 2km)," or (b) drop the expansion mechanic from FR-6 and replace with something that doesn't touch radius (e.g., widen result set via a different criterion). Pick one and make all four passages agree.

2. **[CRITICAL] FR-4's "badge always shown" guarantee is not reconciled with FR-7's "missing fields are omitted" rule — for the one field that can't be allowed to silently disappear**
   - Location: §4.2 FR-4 — "Every list item shows at minimum: name, Free/Paid badge, distance ... address, operating hours" (stated as a hard, testable consequence) versus §4.3 FR-7 — "All fields present in the dataset for that spot are shown; missing fields are omitted rather than rendered as blank placeholders."
   - Why it matters: nothing in the PRD says `parkingType` can never be null/missing in the Mock Dataset. If it can be (and nothing rules it out — §3 Glossary just says the field is `FREE`/`PAID` with no "required, never null" constraint), FR-7's general omission rule would drop the Free/Paid badge for that spot, directly breaking FR-4's "at minimum ... Free/Paid badge" guarantee for the exact field that is, per the Glossary, "the core trust signal the product exists to surface." There is no third state (e.g., "Unclassified") and no rule excluding unclassified spots from results.
   - Fix: add an explicit data constraint — `parkingType` is a required, non-nullable field for every dataset row (enforced at seed time), or add an explicit "Unknown" badge state and decide whether unclassified spots are excluded from `/parking/nearby` results entirely. Either is cheap to write down now; leaving it silent means the architect/story-writer invents the answer.

3. **[CRITICAL] Nothing in the PRD catches, flags, or discloses a stale/wrong Free/Paid classification — the exact failure mode that breaks the product's core promise**
   - Location: §1 Vision — "Success is a driver who trusts the Free/Paid badge enough to act on it without double-checking" — against §3 Glossary, Mock Dataset — "Not live or sensor-fed," and §8 Open Question 3, which admits the dataset's provenance and credibility are still undecided ("Whether the Mock Dataset will be hand-curated or seeded from a real source"). §7 SM-C1 gestures at protecting "classification accuracy" as a counter-metric but defines no mechanism to measure, catch, or correct inaccuracy — there is no "data as of" disclosure to the user anywhere in the UI (§4.3 Spot Detail Panel fields: name, address, price info, hours — no freshness/source indicator), and §5 Non-Goals explicitly rules out any admin surface or user feedback path ("No admin dashboard or spot-management UI" — no "report wrong info" affordance either).
   - Why it matters: this is the single realistic failure mode that most directly undermines the product's reason to exist — a driver who parks on a street tagged Free that's actually metered gets a ticket *because the app told them not to double-check*. Unlike the accessibility/safety NFRs, this gap isn't even tagged `[NOTE FOR PM]` or `[ASSUMPTION]` — it's simply absent, despite being squarely a "Launch-grade" concern the PRD claims to be taking seriously.
   - Fix, cheap and in-scope for a one-day build: (a) a small, always-visible disclosure that classifications come from a static/demo dataset and may not reflect current signage/pricing (a one-line UI string, zero backend work), and (b) decide explicitly in Non-Goals whether "report incorrect listing" is truly out of scope rather than leaving it unaddressed — even declining it should be a stated, deliberate decision, not silence.

4. **[HIGH] Success metrics (SM-1, SM-2) require session-level aggregation the system as specified cannot produce**
   - Location: §7 SM-1 — "% of sessions where the user reaches Route Handoff ... within 60 seconds" and SM-2 — "% of sessions returning zero results ... % that engage the radius-expansion offer" — versus §Cross-Cutting NFRs, Privacy — "not persisted server-side" — and §5 Non-Goals — "No user accounts, authentication, or saved history."
   - Why it matters: computing a "% of sessions" metric requires *some* event/analytics aggregation across sessions server-side (even if anonymized) — there is no FR, NFR, or line in the addendum establishing any telemetry/analytics mechanism at all. As written, these are precise-sounding numeric targets that the described system has no way to produce, which is exactly the "sounds testable, isn't" failure mode — and it sits in direct tension with the Privacy NFR's no-persistence stance.
   - Fix: either add a minimal, explicitly-scoped anonymous event-logging NFR (what's logged, retention, and how it squares with the privacy stance), or mark SM-1/SM-2 as aspirational/post-MVP and say so plainly, rather than presenting them as MVP-validating metrics (§7 says SM-1 "Validates FR-3, FR-4, FR-5, FR-7, FR-8").

5. **[HIGH] FR-3's query-parameter validation is unimplementable as written — "out-of-range" is never bounded, and radius's very presence as a client-supplied param contradicts its "fixed" status**
   - Location: §4.2 FR-3 — "`GET /parking/nearby?lat&lng&radius` returns spots ...; radius is fixed at 1km for MVP (not user-adjustable)." "Out-of-range or malformed `lat`/`lng`/`radius` query params are rejected with a 4xx response rather than silently defaulting."
   - Why it matters: this reads as a precise, testable API contract, but it's not implementable without invented bounds: valid lat/lng ranges are never stated (presumably ±90/±180, but that's a guess); and if radius is genuinely fixed and non-adjustable, it's unclear why the endpoint accepts a client-supplied `radius` at all, what values other than 1 (or 2, per FR-6, see Finding 1) are "in range," or whether the server should simply ignore/override any client value. A story-writer implementing this FR has no way to write a test for "out-of-range" without guessing the range.
   - Fix: state the accepted lat/lng bounds explicitly, and resolve whether `radius` is client-supplied at all (tie this to fixing Finding 1 — if only two fixed values, 1km and 2km, are ever legal, say so and reject everything else).

6. **[HIGH] Manual Area Entry (FR-2) has no defined path from free text to coordinates — geocoding is a silent gap**
   - Location: §4.1 FR-2 — "Manual entry accepts `[ASSUMPTION: a free-text address/area field...]`" and "Once set, a manual Active Location behaves identically to a captured one for FR-3 onward" — versus §4.2 FR-3, whose endpoint only accepts `lat`/`lng`, and `addendum.md` Technical-How, which only budgets a free-tier map provider for "markers + route deep-link," not geocoding.
   - Why it matters: turning free text into `lat`/`lng` requires some geocoding capability (a service, a library, or a curated preset list) — this is a real integration with its own cost/free-tier/failure-mode questions (what happens on an address that doesn't resolve, or resolves ambiguously?), and it is completely absent from both the PRD and its own addendum's tech-how section, even though the addendum explicitly exists to hold this class of implementation detail. An architect scoping the build from these two documents has no answer for where geocoding comes from or what it costs.
   - Fix: add a line to the addendum's Technical-How naming the geocoding approach (even if it's "reuse the map provider's geocoding API" or "a hardcoded preset list of neighborhoods, no free-text geocoding for MVP" — the latter would also resolve Open Question 2 cheaply), and add a Consequence to FR-2 for the no-match/ambiguous-match case.

7. **[MEDIUM] The one quantified performance NFR references an explicitly undetermined variable, making the number unverifiable as stated**
   - Location: §Cross-Cutting NFRs, Performance — "`[ASSUMPTION]` `/parking/nearby` responds within 500ms at demo-scale dataset size" — versus §8 Open Question 3 — "how large/representative [the Mock Dataset] needs to be for the demo to read as credible" is itself still open.
   - Why it matters: "500ms" reads as a precise, testable target, but "demo-scale" is undefined and explicitly left open elsewhere in the same document — the NFR can't actually be verified or falsified until a number the PRD admits it doesn't have yet is settled. This is the "sounds precise but is actually unverifiable" pattern called out directly.
   - Fix: either commit to an order-of-magnitude row count now (e.g., "≤500 rows"), or reword the NFR to make the dependency explicit ("within 500ms once dataset size is fixed per Open Question 3") so it's not presented as a settled, testable target.

8. **[MEDIUM] Route Handoff origin semantics are undefined, and the gap is sharpest for exactly the users who declined location (UJ-2)**
   - Location: §4.3 FR-8 — "The Route action opens the map provider pre-populated with the spot's coordinates/address" (destination only, no mention of origin) — against UJ-1's climax — "The map provider opens with turn-by-turn directions already pointed at the free spot" — and UJ-2, where Arjun explicitly denies location permission and reaches Route via a manually-entered approximate area.
   - Why it matters: it's never decided whether the deep link passes an origin at all. If it doesn't, the external map app will most likely fall back to the device's real GPS position for turn-by-turn — silently using location data the user just declined to share with this app, which sits awkwardly next to the Privacy NFR's careful language about consent. If it does pass an origin for the manual-entry path, that origin is Arjun's approximate manually-set area, not his real position, which could produce a nonsensical route. Neither behavior is chosen, and a story-writer building FR-8 has no way to know which.
   - Fix: state explicitly whether Route Handoff passes an origin parameter, and if so, what it is for the manual-entry case — even "destination-only deep link; origin resolution is left to the external map app and its own permission model" is a fine, cheap answer, but it needs to be written down given the privacy framing elsewhere in the doc.

9. **[MEDIUM] Accessibility NFR is asserted as testable, then undercut by a NOTE FOR PM that doesn't actually narrow the requirement — and the hardest part (keyboard access to map markers) is left completely unaddressed**
   - Location: §Cross-Cutting NFRs, Accessibility — "core flow (view results → detail → route) operable via keyboard" stated as a requirement in the same bullet as `[NOTE FOR PM: full accessibility conformance is unlikely to be fully realized within a one-day MVP — treat as a directional standard, not a launch gate for the hackathon build.]`
   - Why it matters: this is the pattern the review was asked to hunt for — a self-aware NOTE used to wave away a gap rather than fix it cheaply. "Core flow operable via keyboard" as literally written *includes* selecting a map marker (§4.2 FR-5: "Selecting a marker opens the same Spot Detail Panel"), and keyboard-focusable map markers are a well-known hard problem with most map SDKs/canvas renderings — the NOTE doesn't say whether map-marker keyboard access is actually required or not, it just says "don't hold us to full conformance," leaving the exact same ambiguity for whoever implements it.
   - Fix (cheap, in-doc): split the requirement — e.g., "list-view path (results → detail → route) must be fully keyboard-operable; map-marker keyboard access is best-effort for MVP, since the equivalent action is always reachable via the list." That's one sentence and removes the ambiguity instead of just flagging it.

10. **[MEDIUM] Safety NFR uses an unquantified term ("minimal taps") in a document that elsewhere insists on numeric testability**
    - Location: §Constraints and Guardrails, Safety — "critical actions (view detail, route handoff) should be reachable in minimal taps" — compare to the properly-quantified §4.3 FR-7 — "Reachable in one tap/click from either a list item or a map marker."
    - Why it matters: "minimal" is not a testable acceptance criterion, and the document already demonstrates it knows how to write a testable version of this exact claim two sections earlier. Given "Launch-grade" stakes were deliberately claimed, this is a place where the NOTE FOR PM softening ("a full 'do not use while driving' pattern is likely out of scope... revisit if this becomes a real product") is doing work that a one-sentence fix could avoid entirely.
    - Fix: state a number — e.g., "Route Handoff reachable in ≤2 taps from Home" — matching the specificity already used elsewhere.

11. **[LOW/MEDIUM] SM-C1's stated directionality is inverted relative to its own justification**
    - Location: §7 SM-C1 — "Free/Paid classification accuracy must not be sacrificed to drive SM-1 **down** (i.e., faster taps must not come from misleadingly confident badges on uncertain data)."
    - Why it matters: the parenthetical explains the risk as *faster* taps (i.e., driving SM-1 *up*, since SM-1 is "% of sessions reaching Route Handoff within 60 seconds") coming from misleadingly confident badges — but the main clause says accuracy must not be sacrificed to drive SM-1 *down*, which is backwards (nobody would sacrifice accuracy to make the primary metric worse). Whoever implements or monitors this counter-metric will be implementing the wrong guard rail if they follow the literal text.
    - Fix: change "down" to "up," or reword to "must not be sacrificed in pursuit of a faster SM-1."

12. **[LOW/MEDIUM] Addendum quietly commits to `maps.google.com` for the fallback link while the PRD says the map provider is fully unselected**
    - Location: `addendum.md` Technical-How — "'route' can degrade to a plain `maps.google.com` link instead of in-app navigation" — versus `prd.md` §8 Open Question 1 — "Exact map provider is unselected — to be confirmed against current free-tier terms at build time" — and §4.3 FR-8, which only commits to "a plain external maps link" generically, naming no provider.
    - Why it matters: minor, but it's a real prd/addendum disagreement of the kind the review was asked to catch — is Google Maps already the decided fallback (in which case Open Question 1 is only about the *primary* SDK, and should say so), or is the addendum overstepping a decision the PRD deliberately left open?
    - Fix: either narrow Open Question 1 to "primary provider only — fallback is Google Maps, decided," or genericize the addendum line to match the PRD's "a plain external maps link" phrasing.

13. **[LOW] PRD claims to stay implementation-agnostic on backend/frontend choices, then bakes in a concrete REST contract that duplicates the addendum**
    - Location: §Platform — "Backend/frontend technology choices are implementation detail and live in `addendum.md`, not here." — versus §4.2 FR-3 — "`GET /parking/nearby?lat&lng&radius`..." which is close to verbatim with `addendum.md` Technical-How's "single `GET /parking/nearby?lat&lng&radius` endpoint."
    - Why it matters: small, but worth flagging as a scope-boundary inconsistency — the PRD is not actually holding the line it states for itself, which matters for whoever maintains these two documents going forward and wonders which one is authoritative for the endpoint shape.
    - Fix: either drop the literal endpoint signature from FR-3 in favor of a behavior-only description ("a query endpoint accepting a location and returning nearby spots"), or acknowledge in §Platform that the query contract (but not stack choices) is intentionally specified in the PRD.

14. **[LOW] No defined terminal state if the zero-result radius expansion also returns zero**
    - Location: §4.2 FR-6 and UJ-2 both describe exactly one expansion step (1km → ~2km, per the tagged assumption) resulting in a non-zero result. Neither addresses what happens if the expanded search is still empty.
    - Why it matters: a small but real gap for a story-writer — is there a second expansion, a different message, a "try a different area" prompt? Left silent.
    - Fix: one sentence, e.g., "If the expanded radius also returns zero results, the message updates to suggest a different Active Location rather than offering further expansion."
